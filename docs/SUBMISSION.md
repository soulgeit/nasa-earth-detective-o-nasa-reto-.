## High-Level Project Summary

EarthTrend Detective turns students into data detectives. Choose any place on Earth,
or ask a question in English or Spanish, and the tool retrieves real NASA Earth
science data for that place, shows how it has changed over 45 years, and answers the
four questions of the challenge: **what** is changing, **where**, **how much**, and
**whether the change is statistically significant**.

It gives honest verdicts. A trend is called significant only when three independent
tests agree after correcting for autocorrelation (Mann–Kendall with the Hamed–Rao
correction, an autocorrelation-adjusted t-test on the least-squares slope, and the
Theil–Sen confidence interval). When they disagree, the tool says so instead of
picking the loudest one. When the record is too short, it estimates how many more
years of data would be needed, using Weatherhead et al. (1998).

A trend map shows where the same variable rises in one region and falls in another.
An assistant grounded in cited NASA sources suggests what to investigate; it never
generates a number, and a code-level guard rejects any figure that is not in the
statistical result.

The product is bilingual (English and Spanish), needs no account and no installation,
and every result carries the exact query, retrieval date and citation that produced it.

## Detailed Project Description

### 1. What it does

A student types "Is it raining less in Piura?" or clicks a point on the map. The app:

1. **Plans** the question: which NASA variable, which place, which period. Planning
   runs on deterministic rules in the deployed product, so it needs no GPU and gives
   the same answer every time.
2. **Retrieves** the real series from NASA POWER (MERRA-2 reanalysis) through the
   live API — 45 years of monthly data, fetched in about 2 seconds.
3. **Analyses** it: seasonal cycle removed, Theil–Sen slope with a 95 % confidence
   interval, Mann–Kendall with autocorrelation correction, an adjusted t-test, and a
   detectability estimate.
4. **Answers** the four questions in plain language, with a verdict level and the
   number of years still needed.
5. **Cites** its sources: the parameter dictionary, plus NASA Earth Observatory
   articles and method notes about the same variable.

Seven frozen cases open instantly from the gallery, including two that show the tool
being honest: the Antarctic sea ice case reports "no trend detectable so far", and the
Piura rainfall case reports "suggestive", not "significant".

### 2. How it works

**Data.** NASA POWER Monthly API v2.10.0 (MERRA-2 meteorology; CERES/SRB radiation)
for 15 variables, NASA GISTEMP v4 for global temperature anomaly, and NSIDC Sea Ice
Index v4 for Arctic and Antarctic ice. Two Giovanni CSV exports (MERRA-2 temperature
and precipitation over the Amazon basin) are loaded through the upload path. Every
series stores `provenance`: kind, source, model, request URL, retrieval timestamp and
sha256 of the raw response.

**Statistics.** Theil–Sen slope (Sen 1968) with a 95 % bootstrap-free interval;
Mann–Kendall trend test (Mann 1945, Kendall 1975) with the Hamed–Rao variance
correction for autocorrelation (Hamed & Rao 1998); least-squares slope with a
t-test adjusted for effective sample size (Santer et al. 2000); detectability from
Weatherhead et al. (1998). The trend map applies Benjamini–Hochberg false-discovery
control per cell (Wilks 2016).

**The detective.** Retrieval is BM25 over a corpus of 168 verified documents (variable
cards, biome profiles, NASA articles, method notes, glossary), plus optional
embeddings with reciprocal rank fusion. The assistant names the sources it used and
shows them once; the prose never contains a raw URL. A deterministic guard checks
every number against the statistical result, checks that each citation exists, checks
the language, and rejects causal overclaims ("proves", "demuestra") when the verdict
is not significant.

**A fine-tuned model, measured.** A LoRA adapter was trained on a question-to-plan
dataset (4,323 training examples, generated by script; the `<<HUMANO>>`-free parts of
`data/lora/DATASET_CARD.md` describe its known defects). It is a real adapter:
`models/etd-planner-lora/adapter_model.safetensors`, 25,191,536 bytes, sha256
`70314779…7341c`. Measured result:

| Planner | 50 hand-written reference questions | 200 test cases (same generator as training) |
|---|---|---|
| rules | **50/50 (1.000)** | 15.5 % exact variable |
| LoRA | **40/50 (0.800)** on GPU (RTX 4070 SUPER, 4-bit, 2.2 s/question) · 37/50 on CPU | 84.5 % exact variable |

**The product plans with rules, and says so.** The LoRA wins on its own test set and
loses on the hand-written questions, so it is offered as an optional local mode, never
as the default. Both numbers are always published together
(`docs/EVAL_IA.md`, rule 20) — a model result quoted alone would be misleading.

**Huiracocha AI, the conversational layer (round 7).** The assistant that talks in the
app is named after Wiracocha, the Andean creator deity. It is a retrieval-and-rules
system by default, not a free-text generator: it recognises the intent of the message, retrieves
from the cited corpus (BM25 plus a lexicon of everyday words), plans with verified rules
(the LoRA planner is used only on a machine where its model is loaded) and then calls the
same statistics engine that serves the rest of the app. Everything it says is a fixed
sentence, a field of the catalogue, a cited passage, or text written by the statistics
engine, and every reply names the engine that produced it. The catalogue grew from 15 to
35 real NASA POWER variables, each requested live before it was added. `GET /api/scan`
tests every point variable for one place and applies the Benjamini–Hochberg correction
across all of them, so a "confirmed" change has survived the multiple-testing problem.
The "how it works" panel at the top of the app reads its numbers from the running
server (`GET /api/ai/about`) and says which mode that server is in. If the optional
hosted language model is switched on (SI item 4 below), the plan may be proposed by it and
the explanation worded by it, always under the same rules and guard, and the badge and
the panel then say so.

### 3. Why you can trust it

- **Every number is traceable.** The statistical engine computes it; the language
  model never produces one. The guard rejects any number not present in the result.
- **The verdict can say "not significant".** The Antarctic sea ice case does exactly
  that.
- **Disagreement is shown, not hidden.** Lima's temperature is `SIGNIFICANT`, not
  "strong", because the t-test and the detectability estimate do not agree with
  Mann–Kendall. The interface shows which tests agree and which do not.
- **The false-positive rate and interval coverage are measured**, not asserted
  (`tests/stats/test_trend_engine.py`, Monte Carlo).
- **The AI evaluation is published as it came out**, including the LoRA losing to
  the rules on hand-written questions.
- **No filler reaches the statistics.** The NSIDC gap of December 1987 and January
  1988 is `null`, not −9999, and is counted in `n_missing`.

### 4. Who benefits

Students and teachers who want real data without installing anything, in Spanish or
English, on a laptop or a phone. The tool answers the question a student actually
asks ("is it raining less?") and shows the evidence behind the answer, which is what
makes it usable in a classroom rather than a demo.

### 5. What we hope to achieve

We created EarthTrend Detective with three core objectives:

1. **Classroom adoption & empowerment:** Put 45 years of continuous NASA Earth observation data (NASA POWER, GISTEMP, NSIDC) directly into secondary and university classrooms across the Americas and globally, fully bilingual in Spanish and English. Enable students and educators to verify real-world climate claims with one click and zero installation, transforming students from passive information consumers into active data detectives.
2. **Promoting scientific honesty and rigorous uncertainty:** Instill scientific integrity by showing that real science is not about manufacturing alarmist soundbites, but quantifying uncertainty. By reporting honest statistical verdicts—including when trends are non-significant (such as Antarctic sea ice) or when more years of observations are needed (detectability)—we equip students with critical thinking skills against misinformation.
3. **Open-source continuity & global impact:** Maintain the project as an open-source educational platform (MIT License). We plan to expand automated ingestion of global NASA Giovanni and GIBS gridded products, provide curriculum-aligned lab worksheets for teachers, and offer self-hosted container images for schools with limited connectivity.
4. **Target Challenge / Global Award:** Challenge "Tell Us a Climate Story / Earth Science", competing for the NASA Space Apps Challenge 2026 Global Awards in *Best Use of Data* and *Most Inspirational*.

### 6. Tools

Python 3.11/3.12, FastAPI, uvicorn, pydantic, NumPy, SciPy, pymannkendall, requests;
Chart.js and Leaflet for the interface; NASA GIBS Blue Marble tiles and OpenStreetMap
for the basemap. The local fine-tune uses PyTorch 2.6.0+cu124, transformers 5.23.0,
PEFT 0.21.3, bitsandbytes, accelerate, on `HuggingFaceTB/SmolLM2-1.7B-Instruct`.
Versions are pinned in `requirements.txt` and `requirements-ml.txt`.

### 7. Limitations

We would rather state these than let a judge find them:

- **The static backup is limited.** The GitHub Pages link is a frozen copy (the 7 cases
  and 2 trend maps). Live analysis, the assistant, the trend map outside those 2 maps and
  CSV upload need the API, which runs at https://huiracochaia.soulgeit.com.
- **`planned` mission products are declared, not available.** MODIS, OMI, AIRS, GPM
  and GLDAS variables appear in the catalogue as `planned` and cannot be analysed
  until their Giovanni CSV is uploaded. The assistant answers `no_match` and explains
  how to load them.
- **The LoRA is not served publicly.** It needs about 7 GB in float32 or a CUDA GPU.
- **The fine-tune is small**: 150 steps (about 0.28 of an epoch). Its test set comes
  from the same generator as the training data, which flatters it; that is why the
  50 hand-written questions are always reported next to it.
- **Reanalysis caveat.** MERRA-2 trends can be affected by changes in the observing
  system; the app mentions this where it matters.
- **The checklist of reference questions is small**: 50 hand-written questions is
  enough to compare two planners, not enough to claim a general accuracy figure.
  The rules now answer 50/50 on it; a harder set would find more failures.
- **The hosted language model is slower, and its guard checks that a number exists in the
  data, not which one it picks.** With the OpenAI model switched on, planning a question
  took 2 to 5 s and wording an explanation about 7 s (the rules answer in milliseconds);
  the guard sometimes rejects the first attempt and accepts the second. Every number the
  model writes must be in the data, but it may choose a different estimator than the
  headline one: for Lima's 2 m air temperature it quoted the least-squares slope
  (0.13 °C per decade) while the engine's headline is the Theil–Sen slope (0.159 °C per
  decade); both are in the data. If the provider is down, busy or over its daily cap, the
  app answers with the verified rules instead and the panel says so.

- **NASA GIBS** — Blue Marble imagery for the map background.

## Use of Super Intelligence (SI)

**Yes.** Several uses, all disclosed:

1. **SI coding agents wrote most of the code under the team's direction.**
   Tools and models: Claude Code (Claude Opus 5.5, Sonnet 5.5, Fable 5.2) and
   Antigravity (Gemini 3.8 Flash), working as separate agents with named lanes.
   Every generated file starts with a `SI-assisted: <agent> (<model>)` header, and
   each agent's contribution is listed in `docs/AI_USE_LOG.md`. The agents worked from
   the team's design: the "detective + four questions" idea, the choice of cases, the
   decision to publish every AI failure and the decision to deploy rules rather than
   the model are the team's, not the agents'.

2. **The product includes a small open-weight language model fine-tuned with LoRA**
   to turn a question into a structured plan. Base model:
   `HuggingFaceTB/SmolLM2-1.7B-Instruct`. Training data: 4,323 / 814 / 632
   question-plan pairs, **generated by script from templates**
   (`data/lora/DATASET_CARD.md` documents its known defects; measuring the training
   file directly, 101 of the 4,323 examples have an empty year slot, "entre  y .").
   The adapter was trained locally on an RTX 4070 SUPER
   in 353.7 s over 150 steps; training metadata is in `reports/lora/train_meta.json`.
   Its measured performance is published in `docs/EVAL_IA.md`, including the cases
   where it loses to the rules.

3. **The retrieval corpus was assembled with SI assistance** (page downloads,
   extraction, summaries) and each document stores its URL, publisher, language,
   license and a sha256 of the source page. A document whose text is our own summary
   is marked `is_quotation: false` and is never displayed between quotation marks.
   Documents that are literal text from the page are marked as quotations.
   In round 7 the corpus grew from 168 to 999 documents so that five Peruvian cities
   (Lima, Huancayo, Andahuaylas, Ica, Ayacucho) are documented in depth: 124 to 195
   documents each, 340 of them trends computed by our own statistics engine (never
   presented as quotations). Each lane wrote only its own files and every file passes
   `scripts/validate_fragments.py` before it can be pushed.

4. **An optional hosted language model (any OpenAI-compatible API) can propose the plan
   and word the explanation.** It is off unless the operator sets an API key on the
   server; the "how it works" card and the engine badge of the app report live whether it
   is active on the server you are using, and name its host. In the deployed demo it is
   switched on (checked on 2026-11-15): the provider is OpenAI and the model is
   `gpt-4.1-mini`. The model never supplies
   numbers or sources: verified rules check every plan it proposes and overrule it when
   they disagree, and a guard rejects any figure or citation that is not in the NASA
   data (after two rejected attempts the app falls back to the extractive text). The
   provider receives the text of the user's question and, to word an explanation, the
   computed statistics and the cited public passages. Calls are limited (a daily cap, at
   most 8 at once, 20 s each) and the key lives only in the server's environment.
   Code: `src/detective/llm.py`; its failure paths are tested in
   `tests/detective/test_hosted_llm.py` and `scripts/check_hosted_mode.py` (against a fake
   provider: they prove the safeguards, not the accuracy of any model).

**No images or video were generated with SI except the project logo; one audio track was.**
The logo (the Huiracocha AI emblem in the app header, the social-preview image and the favicon)
was generated with SI by the Antigravity agent. The app shows it with a visible "AI-generated"
mark, the preview image carries the same mark, and it is not a NASA logo or mission identifier.
All screenshots are captures of the running application with real data. The narration of the pitch video is an
AI-generated voice (ElevenLabs): the video says so on screen and `docs/AI_USE_LOG.md`
records it; the presenter footage is the team's own. The demo is delivered through the official 7-slide presentation (`docs/demo/EarthTrend_Detective_slides.pdf`), with a 30-second pitch video (`docs/demo/Huiracocha_AI_pitch_30s.mp4`: the presenter, the slides inside an app window and English subtitles) and a companion 29-second screen recording of the real app (`docs/demo/EarthTrend_Detective_30s.mp4`).

The scientific decisions — which tests, which corrections, which threshold, which
cases — are documented with their references in `docs/VALIDACION_ESTADISTICA.md` and
were made by the team.

# Retrieval and planner evaluation (50 hand-written questions)
python -m src.detective.rag.eval
python -m src.detective.rag.eval_plan

# The fine-tuned planner, on GPU or CPU
AI_MODE=full PLANNER_MODEL=local-lora python -m src.detective.rag.eval_plan --planner local-lora

# Who plans by default in the deployed app
AI_MODE=extractive python -m src.detective.rag.eval_plan

# Whole suite, API smoke test, dataset and knowledge validators, secrets scan
python -m pytest -q
